# 3단계 — 로그인 모달: 관심사 분리와 훅 추출

> "UI는 여기, 로직은 여기, API는 여기"처럼 바로 찾을 수 있는 구조를 만든다.
> 분리 자체가 목적이 아니다 — 이 분리가 무엇을 좋게 하는지 한 문장으로 답할 수 있어야 한다.

## 왜 이 과제를 하는가

- 이 모달 하나가 폼 상태, 자동 로그인(토큰 검증·재시도), 로그인 API 호출, localStorage 접근, UI 렌더링을 전부 들고 있습니다. 기능 추가나 수정 때마다 이 파일 전체를 읽어야 합니다.
- 레이어를 가른다는 것은 추상화 훈련이 아니라 "한 번에 한 가지만 읽고 싶다"는 요구입니다. 컴포넌트만 봐도 화면이 그려지고, 훅만 봐도 인증 흐름이 잡히고, service만 봐도 API 스펙이 보여야 합니다.
- 2단계에서 다룬 effect 심문이 여기서 다시 나옵니다. 자동 로그인 effect 안의 재시도 `setTimeout`은 언마운트 이후에도 실행됩니다.

## 실습 대상

`src/components/BackofficeLogin/BackofficeLoginModal.tsx` (약 210줄). 앱의 "3단계 로그인 모달" 탭에서 동작을 확인할 수 있습니다. 테스트 계정은 README에 있습니다.

## 이번 과제

| # | 과제 | 완료 기준 |
| --- | --- | --- |
| 1 | 관심사 분류 — UI / 인증 로직 / API / 저장소로 한 번 훑는다 | 위치 · 관심사 · 분리 후보 · 분리하지 않을 근거 표 1개 |
| 2 | service 분리 — API 호출과 저장소 접근을 컴포넌트에서 뗀다 | 컴포넌트에 `fetch`·`localStorage`가 남아 있지 않음 |
| 3 | 훅 추출 — 자동 로그인·로그인·로그아웃을 훅으로 모은다 | 훅이 한 문장으로 설명됨, 컴포넌트는 폼 상태와 렌더링만 소유 |
| 4 | 흐름 점검 — 재시도와 새로고침 의존을 검토한다 | 검토 결과와 결정(수정 또는 유지 근거) 기록 |

## 어떻게 진행하나

### 관심사부터 분류한다

코드를 위에서 아래로 읽으며 각 블록이 어느 관심사인지 적습니다. 분리하지 않기로 한 곳에도 근거를 답니다. 이번 과제의 절반은 고치지 않겠다는 결정입니다.

### service — React와 무관한 것부터

로그인 API 호출, 토큰 검증 API 호출, 사용자 정보 저장/복원/삭제는 React 없이도 성립하는 코드입니다. service 함수로 내리면 UI 없이 테스트할 수 있습니다.

### 훅 — React 연결만 남긴다

자동 로그인(마운트 시 복원·검증), 로그인, 로그아웃과 `user`·`isLoading` 상태를 훅으로 모읍니다. 훅이 "백오피스 인증 세션을 관리한다" 한 문장으로 설명되는지 확인하세요. 한 문장에 "그리고"가 두 번 들어가면 분리 후보입니다.

### 흐름 점검 — 코드가 하는 약속을 의심한다

1. 토큰 검증 실패 시 `setTimeout`으로 재시도합니다. 모달이 언마운트된 뒤에 이 콜백이 실행되면 무슨 일이 일어나나요? 재시도가 정말 필요한 요구인지부터 판단해보세요.
2. 로그인과 로그아웃이 `window.location.reload()`로 끝납니다. 상태 갱신으로 충분한 자리에서 전체 새로고침에 기대면, 상태 설계의 빈 곳을 새로고침이 메우고 있는 것입니다.

## 셀프 리뷰

1. 컴포넌트 파일만 봐도 화면이 그려지는가. 훅만 봐도 인증 흐름이 잡히는가. service만 봐도 API 스펙이 보이는가.
2. 각 훅을 한 문장으로 설명할 수 있는가.
3. 컴포넌트가 서버 응답의 세부 구조를 직접 알고 있지 않은가.
4. 분리하지 않은 결정에도 한 줄 근거가 있는가.
5. 자동 로그인 흐름을 새로고침 · 잘못된 토큰 · 네트워크 오류 세 경우로 직접 재현해봤는가.
