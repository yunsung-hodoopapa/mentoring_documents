# 5단계 — 에러 하나가 화면을 초당 30번 다시 그린다: 로딩 상태와 렌더 루프

> 서버가 500을 주는데 클라이언트가 초당 30번 요청을 보낸다.
> 재시도 로직은 어디에도 없다. 그런데도 멈추지 않는다.

배달 라이더 앱의 진입 게이트를 고치는 실습입니다. 실제 서비스 장애를 축소 재현했습니다.

앞의 네 단계는 **동작은 되는데 구조가 나쁜** 코드를 다뤘습니다. 이번엔 반대입니다. 구조는 평범하고 흔한데, 특정 조건에서 앱이 무너집니다.

## 왜 이 과제를 하는가

- 라이브러리를 "이렇게 동작하겠지"라고 믿고 쓰다가 생기는 버그를 다룹니다. 우리 코드만 읽어서는 절대 안 보입니다.
- **틀린 답을 붙잡고 있는 시간**을 줄이는 훈련입니다. 이 실습에는 그럴듯하지만 틀린 답이 하나 준비돼 있고, 미션 1에서 직접 태워보고 버립니다.
- 크래시도 에러 로그도 안 남기는 버그를 데이터만으로 좁혀갑니다.

## 실습 대상

`src/components/entry/`. 앱의 "5단계 진입 게이트" 탭에서 동작을 확인합니다.

`lib/` 폴더와 `EntryDevToolbar.tsx`, `RequestCounterPanel.tsx`, `RiderAppScreen.tsx`, `src/mocks/handlers.ts`는 실습 인프라라서 수정 대상이 아닙니다.

## 시작 전에: 관찰 도구

화면 오른쪽 **요청 카운터**는 실제 서비스에서 실사용자 모니터링(RUM) 대시보드로 보던 표를 옮겨둔 것입니다. 엔드포인트별 요청 수, 총 건수, 초당 요청 수, 그리고 컴포넌트별 마운트 횟수를 보여줍니다.

실무에서 이 표를 읽는 게 이 실습의 절반입니다. **숫자를 어떻게 해석하느냐가 진단 속도를 정합니다.**

## 화면 사용법

상단 개발자 도구에서 **구역 API 500**을 켜고 **새로고침**하면 장애 상황이 재현됩니다. 카운터 초기화 버튼으로 표를 비울 수 있습니다. **설정 API 500** 스위치는 미션 4에서만 씁니다. 그전까지는 꺼두세요.

> 500 스위치는 새로고침해야 적용됩니다. 켜기만 하고 새로고침을 안 하면 장애가 재현되지 않아요. **이 사실 자체가 미션 2의 힌트입니다.** 지금은 그냥 넘어가고, 미션 2에서 왜 그런지 설명할 수 있게 되면 됩니다.

## 배경: 지금 구조

라이더가 앱을 켜면 프로필과 배달 구역을 받아야 홈으로 들어갑니다. 둘 중 하나라도 로딩 중이면 스플래시를 보여줍니다.

```
RiderAppScreen                      (QueryClientProvider, 실습 인프라)
└ EntryGuard                        진입 상태 → 화면 모드 결정
   └ EntryShell
      ├ SplashScreen                mode === 'splash'
      └ RiderHomeScreen             mode === 'home'
         ├ useDeliveryZones()       구역 칩
         ├ useRiderSettings()
         ├ useScheduleChanges()
         ├ useNotifications()
         └ useScheduleEvents()
```

판정 로직은 이렇게 생겼습니다.

```ts
// useEntryStatus.ts
if (profileLoading || !profile) return EntryStatus.Loading;
if (zonesLoading) return EntryStatus.Loading;
if (!zones || zones.length === 0) return EntryStatus.NoZones;
return EntryStatus.Ready;

// entryShellPolicy.ts
if (status === EntryStatus.Loading) return ShellMode.Splash;
return ShellMode.Home;
```

읽어보면 이상한 데가 없습니다. 그게 이 실습의 핵심입니다.

## 미션 0: 장애 재현과 관찰

1. 개발자 도구에서 **구역 API 500**을 켜고 새로고침하세요. 5단계 탭으로 이동합니다.
2. 5초쯤 두고 요청 카운터를 읽으세요. 표를 그대로 옮겨 적습니다.
3. **총 건수를 경과 시간으로 나눠보세요.** 초당 몇 건인가요? 이 숫자가 "재시도가 좀 많네"와 "뭔가 계속 다시 태어나고 있다"를 가릅니다.
4. 마운트 횟수 표를 보세요. 어떤 컴포넌트가 계속 다시 마운트되고, 어떤 컴포넌트가 안 그런가요?

### 조용한 것을 보세요

표에서 대부분의 엔드포인트는 수십 번씩 찍힙니다. 그런데 **딱 두 개만 1~2건**입니다.

- `/api/rider/me`
- `/api/rider/me/settings`

이 둘이 왜 조용한지 각각 다른 이유를 찾아내세요. 하나는 **코드의 위치** 때문이고, 하나는 **쿼리 옵션** 때문입니다. (`RiderAppScreen.tsx`, `queries.ts`를 보세요.)

이 두 줄이 **다시 만들어지는 범위의 경계선**을 알려줍니다. 어디부터 어디까지가 죽었다 살아나고 있나요?

### 자가 점검

- 초당 요청 수를 말할 수 있다.
- 다시 마운트되는 컴포넌트와 안 되는 컴포넌트를 구분해 적을 수 있다.
- 조용한 두 엔드포인트의 이유를 각각 한 문장으로 쓸 수 있다.
- "이 앱은 지금 ○○이 반복해서 언마운트/마운트되고 있다"를 한 문장으로 말할 수 있다.

## 미션 1: 첫 번째 답 태워보기

실무에서 이 표를 처음 봤을 때 나온 결론은 이거였습니다.

> "실패한 요청이 계속 재발화되네. **같은 요청이 연속 실패하면 일정 시간 막자.**"

서킷 브레이커라고 부르는 패턴입니다. 그럴듯하죠. 실제로 그렇게 구현해서 커밋까지 했습니다.

직접 해보세요. `src/components/entry/lib/riderApi.ts`의 `get` 함수 맨 앞에 임시로 이런 걸 넣습니다.

```ts
// 미션 1 임시 코드 — 확인 끝나면 지웁니다
const failureCounts = new Map<string, number>();

async function get<T>(path: string): Promise<T> {
  if ((failureCounts.get(path) ?? 0) >= 3) {
    throw new Error(`${path} 차단됨`);
  }
  // ...기존 코드...
  // 응답이 500이면 failureCounts.set(path, (failureCounts.get(path) ?? 0) + 1)
}
```

새로고침하고 카운터를 다시 보세요.

### 여기서 답할 것

1. `/api/rider/me/delivery-zones` 요청은 3건에서 멈췄나요?
2. **전체 요청 수는 줄었나요?** 다른 엔드포인트들은 어떻게 됐나요?

## 미션 2: 왜 다시 로딩이 되는가

이제 진짜 원인을 찾습니다. 관찰된 사실은 이렇습니다.

- `EntryGuard`는 안 죽는데 그 아래(`SplashScreen` / `RiderHomeScreen`)가 번갈아 마운트된다
- 즉 `resolveShellMode`가 돌려주는 값이 `splash`와 `home` 사이를 오간다
- 즉 `useEntryStatus`가 `Loading`과 `NoZones`(또는 `Ready`) 사이를 오간다

`useEntryStatus`에서 `Loading`을 만드는 건 `zonesLoading` 하나입니다. 그러니 질문은 하나로 좁혀집니다.

**이미 500으로 실패한 쿼리를 다시 요청하면, 왜 `isLoading`이 다시 true가 되는가?**

한 번도 성공한 적 없는 쿼리가 error 상태입니다. 여기서 refetch를 걸면 요청이 도는 동안 `isLoading`은 true일까요 false일까요? 이유까지 적어보세요.

### 그다음 소스를 여세요

```
node_modules/@tanstack/query-core/build/modern/query.js
```

이 파일에서 `fetchState`라는 함수를 찾으세요. 5줄입니다. 요청이 시작될 때 쿼리 상태를 어떻게 바꾸는지 보세요.

찾았으면 다음을 설명할 수 있어야 합니다.

2. **개발자 도구에서 500 스위치를 켠 뒤 새로고침이 필요했던 이유**가 이걸로 설명되나요? (새로고침 없이 켜면 구역 데이터가 이미 있는 상태라 무슨 일이 벌어지나요?)
3. `isError`로 이 상황을 감지할 수 있나요? 왜 없나요?

### 자가 점검

## 미션 3: 두 겹으로 막기

원인을 알았으니 고칩니다. **두 군데를 각각 고치고, 각각 단독으로도 루프가 멈추는지 확인**하세요.

### 겹 1 — 상태 매핑

실패 이력이 있는 쿼리의 재요청을 `Loading`으로 보지 않게 합니다.

문제는 판별 방법입니다. `error`는 재요청이 시작될 때 지워지고, `status`는 `pending`으로 돌아갑니다. 재요청 중에도 남아 있는 신호가 하나 있습니다. React Query의 쿼리 결과 객체를 콘솔에 찍어놓고 어떤 필드가 누적되는지 찾아보세요.

찾았으면 판별 함수를 `src/components/entry/lib/` 아래 새 파일로 만드세요. `useEntryStatus`가 쿼리 내부 카운터를 직접 세는 대신 **의도를 읽게** 하는 겁니다.

```ts
// 이런 모양이 됩니다
if (zonesLoading && !hasLoadFailed(zonesQuery)) {
  return EntryStatus.Loading;
}
```

### 겹 2 — 구조적 가드

겹 1만으로도 이 버그는 멈춥니다. 그런데 **다른 쿼리가 같은 상황에 빠지면 똑같은 루프가 다시 생깁니다.**

스플래시는 앱을 켜고 **처음 한 번** 보여주는 화면입니다. 홈이 이미 떠 있는데 스플래시로 되돌아갈 이유가 없어요. 이 규칙을 코드로 만드세요.

`resolveShellMode`가 "홈을 이미 그린 적이 있는지"를 받게 하고, `EntryGuard`가 그 값을 관리합니다.

주의할 점이 하나 있습니다. **`useRef`에 렌더 도중 값을 넣지 마세요.** 렌더에 반영되는 값은 state여야 하고, 실제로 화면에 올라간 렌더만 기록해야 합니다. `useLayoutEffect`가 커밋 직후에 동기로 실행된다는 점을 이용하세요.

### 검증 — 이게 이 미션의 핵심입니다

고치고 나서 카운터가 조용해지면 기분이 좋지만, 그것만으로는 부족합니다.

1. 겹 1만 적용하고 새로고침 → 루프가 멈추는지 확인
2. 겹 1을 되돌리고 겹 2만 적용 → 루프가 멈추는지 확인
3. 둘 다 적용 → 최종 확인

**고친 코드를 잠깐 되돌려서 카운터가 다시 폭주하는 걸 한 번 보세요.** 이걸 안 하면 "고친 것 같은데 사실 다른 이유로 조용해진" 상태를 구분할 수 없습니다.

### 자가 점검

- 500을 켠 채로 새로고침해도 요청이 10건 안쪽에서 멈춘다.
- `RiderHomeScreen` 마운트 횟수가 한 자리다.
- 500을 끈 정상 상태에서 홈 화면이 그대로 동작한다. (구역 칩 3개, 일정·알림·피크 목록)
- 두 수정을 각각 단독으로 껐다 켜보며 효과를 확인했다.
- 겹 2에서 `useRef` 대신 state를 쓴 이유를 설명할 수 있다.

## 미션 5: 수정을 고정하기

지금 상태는 위험합니다. 몇 달 뒤 누군가 `useEntryStatus`를 정리하다가 `!hasLoadFailed(zonesQuery)`를 "불필요해 보이는 조건"이라며 지울 수 있어요. 아무 테스트도 안 깨집니다.

테스트를 씁니다. `npm test`로 돌아갑니다.

### 5-1. 정책 함수 테스트

`src/components/entry/entryShellPolicy.test.ts`에 예시 두 개가 이미 있습니다. 겹 2를 검증하는 케이스를 추가하세요. 홈을 그린 적이 있을 때 로딩이 와도 홈을 유지해야 합니다.

### 5-2. 컴포넌트 테스트 — 이게 진짜입니다

5-1만으로는 부족합니다. `resolveShellMode`에 `hasRenderedHome: true`를 직접 넣어 호출하면, **정작 `EntryGuard`가 그 값을 만들어주는지는 검증되지 않습니다.** latch 코드를 전부 지워도 5-1은 통과합니다.

`EntryGuard`를 렌더하는 테스트를 쓰세요.

- `useEntryStatus`를 모킹해서 상태를 마음대로 바꿉니다 (`vi.mock`)
- 처음엔 `Ready`로 렌더 → 홈이 보이는지 확인
- 그다음 `Loading`으로 바꿔 리렌더 → **여전히 홈인지** 확인

`EntryShell` 아래 실제 화면까지 렌더하면 쿼리가 필요하니, `EntryShell`을 모킹해서 넘어온 `mode`만 보는 방법도 있습니다. 어느 쪽이든 됩니다.

### 5-3. 빨간불을 보세요

**이 미션의 핵심입니다.**

테스트가 초록불이 됐으면, 고친 코드를 잠깐 되돌리세요.

- `EntryGuard`의 latch를 지우고 → 5-2가 실패하는지 확인
- `useEntryStatus`의 `!hasLoadFailed(...)`를 지우고 → 어떤 테스트가 실패하는지 확인

**하나도 안 깨진다면 그 테스트는 아무것도 지키지 못하고 있는 겁니다.** 깨지도록 테스트를 고치세요.

### 자가 점검

- `npm test`가 통과한다.
- latch를 지우면 실패하는 테스트가 있다. 실패 메시지를 PR에 붙일 수 있다.
- `hasLoadFailed` 조건을 지우면 실패하는 테스트가 있다.
- 각 테스트 이름만 읽어도 무엇을 지키는지 알 수 있다.

## 미션 6: 실패 상태 UX

루프는 멈췄습니다. 그런데 500이 계속되는 동안 화면을 보세요.

홈이 떠 있고, 구역 칩 자리에 "구역 없음"이 있고, 라이더는 **아무것도 할 수 없습니다.** 왜 안 되는지도 안 알려주고, 다시 시도할 방법도 없습니다.

> 실제 장애에서도 여기까지가 1차 수정이었습니다. 루프를 멈추는 것과 사용자를 구제하는 것은 다른 문제라, 실패 상태 설계는 후속 작업으로 남겼어요. 그 후속을 여기서 합니다.

지금 판정은 두 가지뿐입니다.

```
로딩 중  →  스플래시
그 외    →  홈
```

"구역을 못 받았다"가 어디에도 없습니다. `zones`가 빈 배열인 것(구역이 정말 없는 신규 라이더)과 못 받은 것(서버 장애)이 같은 `NoZones`로 뭉개져 있어요. **이 둘은 사용자에게 다른 화면을 보여줘야 합니다.**

1. `EntryStatus`에 실패 상태를 추가하세요. 판정은 이미 만들어둔 `hasLoadFailed`로 할 수 있습니다.
2. `ShellMode`에 대응하는 모드를 추가하고, `resolveShellMode`가 그리로 보내게 하세요.
3. 실패 화면을 만드세요. 무슨 일이 일어났는지와 **다시 시도 버튼**이 필요합니다.
4. 재시도는 `queryClient.invalidateQueries` 또는 쿼리의 `refetch`로 겁니다. 500이 계속되면 실패 화면에 머물러야 하고, **재시도가 루프로 번지면 안 됩니다.**

### 함정 하나

재시도를 붙이면 미션 3에서 만든 latch와 부딪힐 수 있습니다. 재시도 중에 화면이 어떻게 되는지 잘 보세요. 실패 화면이 깜빡이거나, 홈으로 튀거나, 카운터가 다시 오르면 설계를 다시 봐야 합니다.

### 자가 점검

- 구역 API 500 상태에서 실패 화면과 재시도 버튼이 보인다.
- 재시도를 눌러도 요청이 1건씩만 늘어난다. 카운터가 폭주하지 않는다.
- 서버를 정상으로 돌리고(500 끄고) 재시도를 누르면 홈으로 들어간다. 새로고침 없이 된다.
- 신규 라이더(구역이 정말 0개)와 서버 장애가 서로 다른 화면으로 갈린다.
- 미션 5의 테스트가 여전히 전부 통과한다. 필요하면 케이스를 추가한다.

## 심화 미션: 관측 설계

이 버그는 실제 서비스에서 **두 달 넘게 아무 알림도 울리지 않았습니다.**
