# 0단계 — 환경과 제출 연습: 기준을 기계에 새긴다

> 본인이 설명할 수 없는 코드는 커밋하지 않는다.
> 이 원칙은 모든 단계에 적용된다. 0단계는 그 원칙을 사람의 의지가 아니라 기계가 지키게 만드는 단계다.

## 왜 이 과제를 하는가

- AI 시대의 병목은 쓰는 속도가 아니라 읽고 판별하는 능력입니다. AI는 명백히 틀린 코드보다 그럴듯하게 틀린 코드를 쏟아냅니다. 이 레포의 모든 단계가 판별 훈련이고, 판별의 최저선을 기계(lint, 타입, 커밋 게이트)가 지킵니다.
- lint와 타입 검사는 결정적입니다 — 같은 코드면 항상 같은 결과. 가장 싼 시점(커밋 전)에 돌아서 버그 비용을 최소화합니다. 이 게이트는 AI가 만든 커밋에도 똑같이 걸립니다.
- 제출 흐름(포크 → 브랜치 → PR)을 실제 과제 전에 한 번 태워봅니다. 1단계부터는 흐름이 아니라 코드에 집중할 수 있게.

## 이번 과제

| # | 과제 | 완료 기준 |
| --- | --- | --- |
| 1 | 커밋 게이트 세우기 — husky + lint-staged로 lint 미통과 커밋을 차단한다 | 고의로 깨진 파일로 커밋이 실제로 막히는 것을 확인한 기록 (PR 본문에 캡처 또는 로그) |
| 2 | 셀프 리뷰 규칙 익히기 — 아래 4단 체크리스트를 읽고 이번 PR에 적용한다 | PR 본문에 체크리스트 수행 표기 |
| 3 | 제출 연습 — 포크 → 브랜치 → 메인 레포 PR 흐름을 이 과제로 밟는다 | 게이트 설치 PR 1개 |

## 어떻게 진행하나

### 커밋 게이트

이 레포에는 ESLint와 Prettier가 세팅되어 있지만, 커밋을 막는 장치는 없습니다. 직접 세우세요.

```bash
npm install --save-dev husky lint-staged
npx husky init
```

`.husky/pre-commit`이 lint-staged를 실행하게 하고, `package.json`에 lint-staged 설정을 추가합니다. 어떤 파일에 무엇을 돌릴지는 스스로 결정하고, 그 근거를 PR에 적으세요. 설정을 통째로 복붙하고 설명하지 못하면 제1원칙 위반입니다.

세웠으면 검증합니다. 일부러 lint가 깨지는 코드를 만들어 커밋해보고, 실제로 막히는지 확인하세요. 검증 없는 안전장치는 없는 것과 같습니다. `--no-verify` 우회는 이 레포 전체에서 금지입니다.

### 셀프 리뷰 4단 체크리스트

리뷰 요청 전, 내 diff를 처음부터 끝까지 직접 읽습니다. 이후 모든 단계의 PR에 적용하는 공통 규칙입니다.

1. **동작** — happy path 말고 로딩 / 에러 / 빈 상태, 그리고 상태 전이(있다→없다, 성공→실패)까지 머릿속에서 돌려봤나
2. **의존성** — import한 것이 실제 존재하나, 기존 유틸을 두고 중복 생성하지 않았나, hook 의존성 배열이 완전한가
3. **타입·린트 침묵** — 새 `any` / `as` / `@ts-ignore` / `eslint-disable`이 없나 (있다면 전부 기계가 경고하려던 자리)
4. **표면적** — 입력을 검증 없이 렌더링하거나 저장하는 곳이 없나

### AI 협업 규칙

AI로 생성한 코드도 머지하는 순간 내 코드입니다. AI를 쓴 부분은 PR 본문에 한 줄로 표기하세요 — "○○는 AI로 생성 후 직접 검토·수정했습니다." 리뷰어에게 어디를 주의 깊게 볼지 알려주는 예의입니다.

## 셀프 리뷰

1. pre-commit 훅이 무엇을 실행하는지 한 문장으로 설명할 수 있는가
2. 게이트가 실제로 커밋을 막는 것을 직접 확인했는가
3. lint-staged 설정의 각 항목을 왜 넣었는지 답할 수 있는가

## 제출

README의 제출 절차대로 포크 → 작업 브랜치(`feat/step-00`) → 메인 레포 PR. 게이트 검증 기록과 설정 근거를 PR 본문에 넣습니다.
